Техническое описание проекта «АуЕда» (ayeda-MVP)

Аудит по факту содержимого репозитория. Где данных нет или они противоречивы — указано явно, без предположений.

================================================================================
1. ОБЩЕЕ ОПИСАНИЕ
================================================================================

- Название: АуЕда (ayeda-MVP), домен ayeda.ru. В README заголовок сломан —
  имя проекта перед тире отсутствует ("#  — Сервис планирования питания и
  покупок 🍽️").
- Назначение: SaaS-платформа для планирования питания — рецепты,
  планировщик меню (календарь/дни/банкет), автогенерация списков покупок,
  обмен рецептами (community), блог, партнёрская доставка продуктов.
- Тип: Full-stack веб-приложение (REST API + SSR-фронтенд) с PWA.
- Целевая аудитория: конечные пользователи (занятые люди/семьи 25–45,
  судя по маркетинговым текстам лендинга), плюс встроенная админка для
  контент-модераторов/администраторов.

7. БИЗНЕС-ЛОГИКА
================================================================================

- Модерация рецептов: обычный автор не может напрямую опубликовать (PUBLIC);
  COMMUNITY-рецепт → PENDING на модерацию, PERSONAL → PRIVATE; staff
  (admin/moderator) может публиковать напрямую через тело запроса.
- Просмотры рецептов: инкремент дедуплицируется через Redis
  setOnce(recipe:view:{id}:{ip}) с TTL 3600 — не чаще раза в час с одного IP.
- Cron: AuthService.cleanExpiredTokens (ежедневно 3:00) — чистка
  просроченных/давно отозванных refresh-токенов; RecipesService.
  reconcileCounters (ежедневно 4:00) — self-healing пересчёт
  commentsCount/likes raw SQL.
- Refresh-токены: ротация на каждый /auth/refresh (старый отзывается, новый
  выдаётся), хранится SHA-256-хэш, не сам токен.
- Лимиты: максимум 20 списков покупок на пользователя (MAX_LISTS_PER_USER);
  throttler 120 запросов/60с глобально (плюс отдельный RateLimitGuard в auth
  — детали не проверялись подробно).
- Внешние интеграции: SMTP (nodemailer, Yandex по умолчанию) для писем;
  партнёрская доставка на лендинге — только текстовые упоминания
  (Ozon/Самокат/Сбермаркет), реальной интеграции с API доставки в коде нет.
- Воркеры/очереди: отсутствуют (BullMQ и т.п. не используется), только
  @nestjs/schedule.

12. ПОЛНЫЙ ПРОМТ ДЛЯ ВОССОЗДАНИЯ
================================================================================

Создай с нуля SaaS-платформу планирования питания «АуЕда» — pnpm-монорепо
(apps/backend, apps/frontend, apps/storybook, packages/shared, packages/ui-kit).

=== СТЕК ===
Backend: NestJS 11 (TypeScript ^5.7), TypeORM 0.3.28, PostgreSQL 15,
Redis 7 (клиент `redis` ^5), JWT-авторизация (@nestjs/jwt, passport-jwt,
argon2 для паролей), class-validator/class-transformer, @nestjs/throttler
(120 req/60s глобально), @nestjs/schedule (cron), Swagger, helmet, multer.
Frontend: Nuxt 4 (Vue 3.5, SSR), Pinia 3 (Composition API стили), @nuxt/ui 4,
@nuxt/icon (Lucide), Tailwind CSS 4, vee-validate + zod, @vite-pwa/nuxt,
isomorphic-dompurify для санитайзинга пользовательского HTML.
Инфраструктура: Docker multi-stage (backend), docker-compose (postgres,
redis, backend, pgadmin), GitHub Actions CI (lint→type-check→test→build,
backend дополнительно e2e с сервис-контейнерами БД/Redis).

=== АРХИТЕКТУРА BACKEND ===
Строгая слоистость: Controller (только транспорт: guards, DTO, вызов
сервиса) → Service (вся бизнес-логика, проверка владения ресурсом через
ForbiddenException, транзакции через DataSource.transaction) → Repository
(TypeORM) → PostgreSQL. Redis — только через utils/redis.utils.ts
(cacheGetOrSet, clearCachePattern/getKeysByPattern — SCAN, никогда KEYS).
Каждый модуль: <feature>.module/controller/service.ts, dto/
(create/update/response/query), entities/, опционально enums/guards/.
Ошибки — только HttpException, единый AllExceptionsFilter (main.ts) →
{statusCode,error,message,path,timestamp}, 5xx логируется без утечки
стека клиенту. Миграции — вручную (не migration:generate as-is), имя
<PascalCase><unix-ms>, обязательный рабочий down(), synchronize:false.

=== ДОМЕННЫЕ МОДУЛИ (20) ===
auth (register/login/refresh-ротация с SHA-256-хэшем токена и revoke
старого/logout(-all)/verify-email/forgot+reset-password/change-password,
access 15м + refresh 7д, роли user/moderator/admin, cron очистки
просроченных токенов ежедневно в 3:00);
users (CRUD admin, /me, Redis-кэш 5 мин, admin-статистика кэша через SCAN);
recipes (title/description/cookingTime/servings/calories/difficulty
easy|medium|hard/status draft|private|pending|public|rejected/type
personal|community/photo jsonb/video/steps jsonb/srcPath-slug/seo jsonb/
tsvector полнотекстовый поиск/soft delete; модерация: community→pending,
personal→private для обычных авторов, staff публикует напрямую; Redis-
дедуп инкремента просмотров 1 раз/час/IP; cron self-healing пересчёта
commentsCount/likes ежедневно в 4:00; поиск public/my/favorites/all);
ingredients/categories/units (справочники CRUD admin/moderator, у
ingredients — авто-генерация slug транслитерацией + nutritionInfo jsonb);
recipe-ingredients/recipe-categories (M2M-связки);
comments (вложены в рецепт, скрытие/показ модератором, очередь модерации);
likes/favorites (toggle-эндпоинты, Unique(recipeId,userId), статус,
списки пользователя);
menu-planner (списки меню displayType DAYS|BANQUET, дни (dayOrder,title),
слоты (slotType, dayId?, slotDate?, mealType?, order), позиции-рецепты в
слотах с notes/order, reorder дней и позиций через транзакцию с проверкой
владения на каждый элемент, выборка слотов по диапазону дат, авто-создание
banquet-слота при первом добавлении блюда в банкет);
shopping-lists (списки с shareToken для публичного доступа без авторизации
по /shared/:token, лимит 20 списков/пользователь, позиции с category/
quantity/unit/price/isChecked/sortOrder, bulk-добавление с шагом sortOrder
1000, copy с обязательным isChecked:false и сбросом shareToken, reorder в
транзакции с проверкой владения);
shopping-categories (справочник категорий покупок: id/code/name/icon/
sortOrder/isActive);
articles (draft/published, slug, steps jsonb, soft delete, публичный
доступ по slug + отдельный по id для редактирования);
uploads (авторизованная + публичная загрузка, MulterModule memoryStorage
лимит 10MB на уровне модуля, allow-list mimetype image/jpeg|png|gif|webp,
расширение сохраняемого файла ВСЕГДА выводится из провалидированного
mimetype через карту ALLOWED_MIME_TO_EXTENSION — НЕ из клиентского
originalname, иначе возможен stored XSS через spoofing расширения;
абстракция StorageService/IStorageService с local-реализацией, S3 —
заглушка с throw);
dashboard (агрегированная статистика для admin/moderator);
email (nodemailer, SMTP, письма верификации/сброса пароля с токеном-
ссылкой на FRONTEND_URL);
health (GET /health без версии — проверка Postgres SELECT 1 + Redis PING,
200 при ok, 503 при degraded, {status,db,redis,uptime,timestamp});
redis (глобальный провайдер клиента Redis).

=== АУТЕНТИФИКАЦИЯ ===
Access-JWT в заголовке Authorization: Bearer, refresh-JWT ротируется на
каждый /auth/refresh (старый revoke, новый выдаётся), хранится только
SHA-256-хэш refresh-токена в БД (не сам токен). JwtStrategy подгружает
User из БД в req.user с Redis-кэшем 5 мин. RolesGuard + @Roles() decorator
по метадате Reflector. JwtAuthGuard — защищённые роуты; OptionalJwtAuthGuard
— публичные с опциональным пользователем. Throttler на чувствительных
роутах через @Throttle.

=== FRONTEND ===
SSR через Nuxt routeRules (главная/каталоги — ssr:true, cabinet/admin/auth
— ssr:false SPA-режим, /api/** проксируется через Nitro server route на
runtimeConfig.public.apiBase). Все запросы к API — через единый composable
useApi() (bearer-заголовок, автоматический refresh-и-повтор при 401),
доменные composables (useRecipesApi, useUsersApi, useMenuPlannerApi и т.п.)
оборачивают его. Pinia-сторы Composition API: userStore, menuPlannerStore,
shoppingListsStore, notificationsStore, uiStore. Формы — vee-validate+zod.
PWA — @vite-pwa/nuxt с runtime-caching (изображения CacheFirst 30д,
API NetworkFirst 1д). Единственный v-html в приложении (страница статьи
блога) — ОБЯЗАТЕЛЬНО оборачивать в DOMPurify.sanitize() перед рендером
(isomorphic-dompurify для SSR-совместимости), контент статьи пишут только
admin/moderator, но без санитайзинга — persistent XSS при компрометации
аккаунта. Резолв относительных путей к медиа (аватары/фото рецептов) в
абсолютный URL — через единый composable useImageUrl (path.startsWith
('http') ? path : apiUrl + path с проверкой ведущего слеша), не дублировать
логику по компонентам. Middleware auth.global.ts/admin.global.ts защищают
/cabinet/** и /admin/** соответственно.

=== БД ===
25 миграций вручную (не generate as-is), стиль имени
<PascalCase><unix-ms-timestamp>, рабочий down() у каждой, synchronize:false
всегда. Порядок сущностей: users→refresh_tokens→units→categories→
ingredients→recipes→recipe_ingredients→recipe_categories→likes→favorites→
comments→uploads→(seo/unit_id доп.колонки)→menu_planner_tables→
shopping_lists_tables→articles→(счётчики comments/views)→articles_steps→
(доп. поля ingredients)→(чистка legacy refresh tokens/индексов/enum'ов
articles).

=== КОНФИГУРАЦИЯ ===
backend .env: PORT=4000, DB_HOST/PORT/USERNAME/PASSWORD/DATABASE,
DB_LOGGING, REDIS_URL, JWT_ACCESS_SECRET/REFRESH_SECRET,
JWT_ACCESS_EXPIRES_IN=15m/REFRESH_EXPIRES_IN=7d, CORS_ORIGIN, UPLOAD_DIR,
MAX_FILE_SIZE=5242880, STORAGE_TYPE=local, BASE_URL, + SMTP_HOST/PORT/
USER/PASSWORD и FRONTEND_URL (обязательны для EmailService, не забыть
в .env.example). frontend .env: NUXT_PUBLIC_API_BASE_URL,
NUXT_PUBLIC_APP_URL, опционально Sentry DSN/Яндекс.Метрика.

=== ТЕСТЫ ===
Backend: Jest unit (transformIgnorePatterns должен явно разрешать
транспиляцию @nestjs/schedule — это чистый ESM-пакет, иначе тесты cron-
сервисов не соберутся) + отдельный jest-e2e.json конфиг с реальными
Postgres/Redis (service-контейнеры в CI). Frontend: Vitest для unit,
Playwright для e2e (обязательно завести playwright.config.ts с baseURL
и webServer — без него тест не запустится).

=== ЧЕГО НЕ ДЕЛАТЬ (уроки этого проекта) ===
Не использовать Redis KEYS (только SCAN); не хранить бизнес-логику или
прямые обращения к БД/Redis в контроллерах; не строить расширение
сохраняемого файла из клиентского имени файла; всегда санитайзить
пользовательский HTML перед v-html; не дублировать одну и ту же функцию
резолва URL по многим компонентам — выносить в composable; при вычислении
следующего порядкового номера (sortOrder) из raw SQL агрегатов (MAX(...))
всегда явно parseInt — значение из Postgres приходит строкой, и оператор +
в JS сделает конкатенацию, а не сложение, если хотя бы один операнд —
непустая строка.
